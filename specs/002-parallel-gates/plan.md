# 002 — plan

## Approach

Add `pytest-xdist` and use it where wall time matters: the CI `checks` test step, the
golden workflow and the two test steps of the release workflow. No code under `src/` or
test logic changes. Locally plain `uv run pytest` stays serial; parallelism is opt-in and
documented.

Every parallel command spells out `-n auto --dist loadgroup` in full. `--dist` does not go
in `addopts`: without `-n`, xdist leaves `dist` at `loadgroup`, pytest-benchmark reads
that as xdist being active, skips timing and fails the run on its warning (the
plan-reviewer reproduced this with the documented `--benchmark-enable` command), and
`-p no:xdist` then rejects `--dist` as unknown.

Under `loadgroup` every test is distributed one by one except tests sharing an
`xdist_group` mark, which run as one block on one worker. Six golden modules paint a whole
map once in a module-scoped fixture (setup times from the serial golden run, 2026-10-27):
`tests/golden/test_parity.py` (62 s), `tests/unit/maps/test_attribution.py` (59 s),
`test_pipeline_letter_compose.py` (51 s), `lettering/test_notes.py` (48 s),
`test_route_ink.py` (43 s) and `test_pipeline_fetch_paint.py` (43 s). Ungrouped, each
worker that receives one of their tests repaints, up to four times. Each of those modules
gets one `xdist_group` named after the module (`"test_parity"`, `"test_attribution"`,
`"test_pipeline_letter_compose"`, `"test_notes"`, `"test_route_ink"`,
`"test_pipeline_fetch_paint"`), applied beside its existing `golden` mark: in `pytestmark`
for `test_parity.py`, on each `@pytest.mark.golden` class otherwise, so every class of a
module shares one group. The other golden modules (`test_docs_images.py`,
`test_places.py`, `test_map_styles.py`, `test_cli.py`, `test_route_map_example.py`) paint
per test and stay ungrouped. Non-golden module fixtures (`painter/test_smoke.py`'s 2 s
`job` and smaller) are left: their repeat cost is seconds.

`xdist_group` is registered only while xdist is loaded, and `--strict-markers` is on, so
it is also registered in `[tool.pytest.ini_options] markers`; without that, a run with
xdist absent (the `prerelease` job, `-p no:xdist`) fails to collect the six modules.

`--dist loadscope` was rejected: it pins each whole module to one worker, so the 32 docs
image tests (about 14 minutes serial) would run on one worker.

Benchmarks stay serial. pytest-benchmark disables itself under xdist, and CodSpeed's
instrumentation counts one process. The CI benchmark smoke step and `codspeed.yml` keep
their current commands. The `prerelease` job (Python 3.15, hand-installed plugins) stays
serial and unchanged: with nothing in `addopts` it needs no xdist.

No boundary or public-API change, so no ADR.

## Test plan

This change adds no test: the existing suites are the check, run under the new commands.
Timings run with nothing else on the machine, and "after" uses the same flags as "before"
(both with `--golden-tolerance`).

1. Fast selection, parallel: `uv run pytest -m "not golden and not benchmark"
   --golden-tolerance -n auto --dist loadgroup` passes three times, with
   `--randomly-seed=1`, `=2` and `=3`. Record the wall time of the first.
2. Coverage under xdist: the CI test command with `--cov`, then both `coverage report`
   gates pass; compare their percentages with a serial `--cov` run (equal to two decimals).
3. Golden timing: `uv run pytest -m golden --golden-tolerance -n auto --dist loadgroup`
   passes; record wall time, and peak memory: the controller's and each worker's RSS
   from `ps` every second (their peaks and the peak of their sum) and the cgroup's `memory.peak` (if `/sys/fs/cgroup/memory.peak` exists, read it
   before and after).
4. Golden exact, as a separate pass/fail: `uv run pytest -m golden -n auto --dist
   loadgroup`. An exact failure that also fails serially on `main` goes to `docs/issues/`
   with a GitHub issue and does not block this change; one that passes serially blocks it.
5. Each grouped module paints once: `uv run pytest -m golden -n 4 --dist loadgroup -vv
   --durations=0 --durations-min=10` over the six grouped modules. Required: every test of
   a module carries the same `[gwN]`, and the durations list exactly one `setup` of 40 s
   or more per module.
6. The marker without xdist: `uv run pytest -p no:xdist --co -q
   tests/golden/test_parity.py tests/unit/maps/test_route_ink.py` collects without error.
7. Plain serial run unchanged: `uv run pytest tests/unit/test_placeholder.py` runs with no
   workers.
8. Benchmarks: `uv run pytest -m benchmark` passes, and
   `uv run pytest -m benchmark --benchmark-enable` exits 0 and prints a timing table.
9. `prek run --all-files`, `ruff`, `ty`, `lint-imports` green.
10. CI: `checks` and both golden runners green; record their times from the PR's runs.

The macOS rule: macos-15 runners have 3 cores and 7 GB. If the controller's RSS plus three
times the largest worker peak (from step 3) exceeds 5 GB, macOS gets `workers: 2`;
otherwise `auto`.

Acceptance criteria map: dependency → `pyproject.toml`/`uv.lock`; serial by default →
step 7; `checks` parallel with coverage → steps 1, 2; golden both runners → step 10;
each module paints once → step 5; benchmarks serial → step 8 and the unchanged
workflows; memory → step 3 and the macOS rule; times → PR body and the feature note;
docs → `CONTRIBUTING.md`, `CLAUDE.md`; pins exact → step 4 and no golden file in the
diff.

## Delegation

Small enough to stay in the main context: about 20 changed lines across eleven files, plus
measurements. The plan-reviewer gate is dispatched (fresh context). The golden runs go to
background shells so the main context reads only their summary lines. A fresh-context
diff review against this plan runs before the PR.

## File-ownership partition

One track, in order: dependency and marker registration → group marks → local checks →
workflows → docs. No concurrent work, so no worktrees.

## Decisions

- Serial by default locally, and `--dist` on the command line rather than in `addopts`:
  a failing test's output stays in order, a debugger works, and benchmarks keep timing.
- `loadgroup` over `loadscope`, for the reason above.
- `publish.yml` runs in parallel too: it gates releases on the same suites.
- No hard time budget: the maintainer's call (2026-10-27).
- No matrix sharding of the golden job yet: measured parallel time decides whether it is
  worth a follow-up.
- Plan review is in `review.md`: round 1 (BLOCK, 8 findings, all taken), round 2 (BLOCK on
  a stale `tasks.md`, rewritten; per-process RSS logging taken), round 3 (PASS).
- The macOS check keeps its name: the job sets `name: golden (${{ matrix.os }})`, since the
  `include` key would otherwise rename it `golden (macos-15, 2)` and a required check on
  the old name would never report (diff review, 2026-10-27).
