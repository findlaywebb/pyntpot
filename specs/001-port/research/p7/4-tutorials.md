# P7 research 4: what makes tutorials and how-to guides great

Angle: tutorial arc, first success, output at every step, keeping tutorial code tested,
voice, how-tos and troubleshooting, and choosing which how-tos to write. Case studies
first, then learning research, then implications for pyntpot.

## 1. Case studies

**Diátaxis (Daniele Procida).** The tutorial page (https://diataxis.fr/tutorials/) is the
best single checklist: "Deliver visible results early and often", "Maintain a narrative of
the expected" (tell the reader what they should see, show sample output, flag likely
mistakes), "Point out what the learner should notice", "Ruthlessly minimise explanation"
(link to it instead), "Ignore options and alternatives", "Encourage and permit
repetition" and "Aspire to perfect reliability". The how-to page
(https://diataxis.fr/how-to-guides/) is the mirror: "Choose titles that say exactly what a
how-to guide shows", it serves "the already-competent user", it is written "from the
perspective of the user, not of the machinery", it must be "adaptable to real-world
use-cases", and "practical usability is more helpful than completeness". The comparison
page (https://diataxis.fr/tutorials-how-to/) puts it as "at study" versus "at work", and
places responsibility differently: in a tutorial "responsibility lies with the teacher",
in a how-to the reader handles their own surprises, so the guide must prepare them for
them. Procida's PyCon AU 2017 talk "What nobody tells you about documentation"
(https://www.youtube.com/watch?v=t4vKPhjcMZg) adds the driving-lesson analogy: a tutorial
is a lesson in which the learner must succeed, not a tour of features.

**Django polls tutorial** (https://docs.djangoproject.com/en/5.2/intro/tutorial01/). Eight
parts, each one sitting. Part 1 opens with "Let's learn by example", names the finished
artefact (a poll app with a public site and an admin site) and makes the reader check
their install with one command whose output is shown. The first success is concrete and
named: "You'll see a 'Congratulations!' page, with a rocket taking off. It worked!" The
expected terminal output is printed in full, including a warning the reader will see, with
"Ignore the warning about unapplied database migrations for now". That pre-empting of the
harmless scary line is a pattern worth copying. Troubleshooting is inline callouts ("Page
not found? ... check that you're going to /polls/ and not /") plus a "Where to get help"
line, not a separate chapter.

**The Rust Book** (https://doc.rust-lang.org/book/). Alternates concept chapters with
three project chapters (2, 12, 21). Every program is a numbered Listing with a caption and
file name, and the expected output follows it ("the string `Hello, world!` should print to
the terminal", with a pointer back to Troubleshooting if not:
https://doc.rust-lang.org/book/ch01-02-hello-world.html). It deliberately shows code that
fails, marked with Ferris icons ("This code does not compile!", "This code panics!",
https://doc.rust-lang.org/book/ch00-00-introduction.html), because reading the error is
part of the skill. Its machinery is the strongest model for us: every non-trivial listing
is a real Cargo project under `listings/`, pulled into prose with `{{#rustdoc_include}}`
and anchor comments; each listing's output is captured in `output.txt` and regenerated by
`tools/update-rustc.sh`, and output that cannot be scripted carries a
`manual-regeneration` comment so it can be grepped
(https://github.com/rust-lang/book/blob/main/ADMIN_TASKS.md).

**FastAPI** (https://fastapi.tiangolo.com/tutorial/). "Each section gradually builds on the
previous ones, but it's structured to separate topics, so that you can go directly to any
specific one": a tutorial that doubles as a later reference. "All the code blocks can be
copied and used directly (they are actually tested Python files)": snippets live in
`docs_src/` and `tests/test_tutorial/` imports each one by name. Each step is a whole
runnable file, not a fragment, with the changed lines highlighted.

**Flask tutorial** (https://flask.palletsprojects.com/en/stable/tutorial/). Eleven short
pages building one app, Flaskr. The index page shows three screenshots of the finished
product before any code, says what it assumes ("already familiar with Python"), says what
it leaves out, and links the finished project in the repo "if you want to compare your
project with the final product". It ends with "Keep Developing!", a page of next steps.

**Elm guide** (https://guide.elm-lang.org/). Opens with a running counter before any
explanation, "Try it out in the online editor", and admits "The code can definitely look
unfamiliar at first". Show the whole working thing, then take it apart.

**Svelte tutorial** (https://svelte.dev/tutorial/svelte/welcome-to-svelte). Prose beside a
live editor, one small concept per page, a "solve" button, and the advice that "you will
learn faster by ... manually typing it in". The step size is the lesson: dozens of tiny
pages rather than a few long ones.

**polars user guide** (https://docs.pola.rs/user-guide/getting-started/). Snippets are
real files under `docs/source/src/python/` included by section marker
(`--8<-- "python/user-guide/getting-started.py:df"`) inside a
`python exec="on" result="text"` block, so the output shown on the page is produced by
running the code at build time. Prose and output cannot drift.

**pandas cookbook** (https://pandas.pydata.org/docs/user_guide/cookbook.html). "Short and
sweet examples and links", grouped by topic, many entries just a StackOverflow link. It is
a warning as much as a model: titles are the reader's question, which is right, but
without tested code and with thin context, entries rot. A how-to section should keep the
goal titles and lose the link farm.

**Learn Python the Hard Way** (https://learnpythonthehardway.org/python3/intro.html). "You
must type each of these exercises in, manually", "Type in each file exactly", "Make it
run". The useful idea for us is not the austerity but the "what you should see" block after
every exercise, and the claim that typing builds attention to detail.

**Julia Evans.** Her zines and posts teach from one concrete, specific thing she actually
did, often a struggle (https://jvns.ca/blog/2021/05/24/blog-about-what-you-ve-struggled-with/,
https://jvns.ca/blog/2023/08/07/tactics-for-writing-in-public/). The transferable habits:
small scope per page, a drawing or real output on every page, and plain first-person
wonder ("this is what happens, isn't that neat") instead of authority. For a library whose
product is a picture, "a picture on every page" is not a stretch.

**Stripe quickstarts** (https://docs.stripe.com/quickstarts). Prose in the middle, complete
runnable code alongside it with the relevant lines highlighted as you scroll, sandbox keys
issued without sign-up so nothing blocks the first run. The design target is removing every
precondition between the reader and the first success.

**The Little Schemer.** Question and answer frames, each a tiny step, with "Commandments"
stated only after the reader has done the thing several times. Relevant as a rule:
generalise after the concrete, never before. Diátaxis says the same ("focus on the
concrete").

## 2. What learning research adds

- **Worked-example effect and cognitive load.** Novices learn more from studying complete
  worked examples than from solving problems unaided (Sweller and Cooper 1985;
  https://en.wikipedia.org/wiki/Worked-example_effect). Greg Wilson's *Teaching Tech
  Together* (https://teachtogether.tech/en/index.html#s:architecture) summarises the
  follow-ons: **faded examples** ("Each successive problem gives the learner less
  scaffolding"), **labelled subgoals** ("giving names to the steps in a step-by-step
  description"), and **Parsons problems**.
- **Expertise reversal** (Kalyuga et al. 2003;
  https://en.wikipedia.org/wiki/Expertise_reversal_effect; Wilson, `#g:expertise-reversal`):
  the scaffolding that helps novices slows experts. That is the research case for keeping
  tutorials and how-tos as separate documents.
- **Show output at every step.** Every exemplar above prints what the reader should see
  after every action. It is how the learner checks themselves without a teacher, which is
  Diátaxis' "narrative of the expected" and its reliability rule in one.
- **Time to first success.** No reliable study gives a number, but the shared practice is a
  first visible result within minutes and before any concept is explained (Elm's counter,
  Django's rocket, Rust's hello world). The obstacle is nearly always setup, so the best
  tutorials remove preconditions (Stripe's keyless sandbox) rather than explain them.

## 3. Keeping tutorial code tested: the options

1. **Doctest in Markdown** (Sybil, https://sybil.readthedocs.io/en/latest/use.html, or
   pytest-markdown-docs). Good for small REPL snippets; awkward for programs that write
   images.
2. **Literate includes from tested files** (Rust Book `{{#rustdoc_include}}`, polars and
   pymdownx Snippets with `[start:name]`/`[end:name]` markers and `check_paths: true`).
   The prose shows a region of a script the test suite already runs. Requires a site
   generator: GitHub's Markdown renderer does not expand includes.
3. **Executed at build time** (polars `exec="on"`, Rust `output.txt` regeneration). Output
   shown is output produced.
4. **Verbatim copy plus a sync check.** The fenced block in the Markdown is checked by a test
   to be an exact substring of the named script. Renders on GitHub, needs no site generator,
   fails the gate on drift.

## 4. How-to guides and troubleshooting

- Title is the goal in the reader's words: "How to point pyntpot at your own Overpass
  server", not "Providers". Django's how-to index (https://docs.djangoproject.com/en/5.2/howto/)
  is goal-titled throughout.
- Assume the tutorial; link it and the reference instead of re-teaching.
- Open with one line of "you need" (what must already exist) and end with how to confirm it
  worked.
- Allow branches ("if your server needs authentication ..."): Diátaxis says a how-to is not
  merely a procedure.
- **Troubleshooting** in the exemplars is local, not a separate FAQ: Django and Rust put a
  callout at the step where the failure happens, keyed by the symptom the reader sees (the
  error text, the wrong picture). Use a separate page only for errors that can arise from
  many places.
- **Choosing which how-tos to write.** Sources, best first: questions real users ask
  (issues, the upstream consumer's migration in P8), each place a tutorial says "ignore
  this for now", each configuration seam the public API exposes (a public parameter with
  no guide is a how-to waiting), and the tasks a maintainer does repeatedly. Write the few
  that unblock real use; do not write one per feature.

## 5. Implications for pyntpot

### The arc: one tutorial in two halves, not eight pages and not one map page

The rung scripts already form a faded, subgoal-labelled sequence: each module docstring
names the public names it introduces, rungs 4 and 7 introduce nothing new (rehearsal, the
Little Schemer's repetition), and rung 8 swaps primitives for the four stages. Propose:

- `docs/tutorials/paint-a-watercolour.md`, rungs 1 to 7: "paper, wash, brush, nib,
  pigments, lettering, a composed sheet". One page with one section per rung (Django-sized
  parts would be too thin: each rung is 45 to 140 lines and runs in seconds).
- `docs/tutorials/first-map.md`, rung 8: the application, linking back to the first
  tutorial for what `paint` is doing underneath.

This differs from the P7 outline, which names only `first-map.md`. A map-only tutorial
would leave seven tested scripts unexplained and contradict ADR 0026's stated reason for
the widening ("The tutorials start from the painting primitives ... and only then paint a
route map"). An index page `docs/tutorials/README.md` should give the order and say both
halves stand alone.

### Each rung section, same shape

1. One sentence of what you will paint, with the finished PNG shown first (Flask, Elm).
2. The run command and the log line it prints (`INFO ... wrote out/wash.png`).
3. The image.
4. The `main` body quoted verbatim, with the new names in it bolded in prose and linked
   to reference.
5. "What to notice": one or two things in the image (the pigment pooled just inside the
   wash's edge; the dry stroke breaking on the paper's tooth; multiply versus glazing side
   by side in rung 5).
6. One "try changing" line that reruns safely: a different seed, `"wood"` for `"water"`,
   `TURNS = 5`. Diátaxis' "permit repetition".

### First success

Rung 1 is the first success, and it must happen in under five minutes from `pip install`:
one command, one cream sheet with a worn border. It is offline and deterministic, which the
map is not. For `first-map.md` the first run needs a GPX file, network access and a
contact string, three preconditions a newcomer may lack. The Lynmouth fixture
(`tests/fixtures/lynmouth/`, 3.5 MB, a track plus cached payloads) sits in `tests/` and is
not in the wheel. Proposal: make it downloadable (a release asset or a `docs/` link to the
files on GitHub) so the tutorial's first map paints from cache with no request, exactly as
`tests/examples/test_route_map.py` already proves; then a second step paints the reader's
own GPX against the public servers. That is Stripe's "remove the precondition" applied.
Pre-empt the harmless log lines the first live fetch prints, as Django does with the
migrations warning.

### Keeping prose in sync with the tested scripts

The docs are plain Markdown read on GitHub, with no site generator, so includes (option 2)
do not render. Use option 4, in the repo's own idiom:

- Tutorial code blocks are copies of script regions, each preceded by a marker such as
  `<!-- from examples/wash.py: main -->`.
- A new architecture test, `tests/architecture/test_tutorials.py`, checks every marked
  block is a verbatim substring of the named script, that every rung script is quoted by
  some tutorial, and that every `uv run python examples/...` command in the prose names an
  existing script.
- The images in the tutorial are the scripts' outputs, committed under
  `docs/tutorials/images/` and regenerated by one documented command; a test compares
  each committed image with a fresh run under the existing `--golden-tolerance` rule. The
  scripts are seeded, so this is cheap and exact locally.
- If a site generator is adopted later, the markers become pymdownx Snippets includes with
  `check_paths: true` and nothing else changes.

### Candidate how-to guides, with reasons

Keep the three planned, reframed as goals, and add four:

1. **Paint a map from your own GPX file with the command line** (`pyntpot map`). The CLI is
   public and the tutorial uses the script, so the most common real task has no guide.
2. **Point pyntpot at your own Overpass and OpenTopoData servers**
   (`self-host-providers`). Public: `OverpassFeatures(contact, endpoints, budget=...)` and
   `OpenTopoData(contact, url, ...)`. Note that writing a *new* provider is not possible
   with public names (`Features` and `Elevation` are not in `pyntpot.maps.__all__`), so the
   guide must say it covers self-hosting the same services only, or P7 must decide to
   publish the protocols (an ADR).
3. **Write a theme** (`write-a-theme`). `Style.from_toml` needs a table for every group and
   rejects unknown keys, so the guide's first step is copying the packaged
   `default.toml` (via `importlib.resources`) and editing it; troubleshooting keyed on the
   `pydantic.ValidationError` messages a reader will hit.
4. **Change the route's colour and width** (`Style.with_route_ink`). The upstream consumer
   needed exactly this (P8); the commonest tweak should not require a whole theme.
5. **Paint your own shapes with the engine** (`use-the-engine-without-maps`), reframed so
   it does not repeat rungs 1 to 7: start from the reader's own mask (a polygon rasterised
   with Pillow, an image's alpha) and lettering along their own path. The tutorial teaches
   the primitives; the how-to adapts them.
6. **Work offline and reuse the cache.** What the cache holds, how the key is formed,
   when a repaint happens; links to the cache-layout reference.
7. **Credit the map data correctly.** `attribution=False` exists; the guide says when the
   licences still require a credit and how to place it.

Defer annotations and `candidate_export` until a user asks: they are public but the rung
script deliberately leaves them out.

### Changes to the P7 outline

- Add `docs/tutorials/paint-a-watercolour.md` (rungs 1 to 7) before `first-map.md`.
- Ship or link the Lynmouth sample so the first map can be offline.
- Add `test_tutorials.py` (sync and image checks) to P7.2's gate.
- Add the four how-tos above or record them in the backlog; reframe
  `use-the-engine-without-maps` as adaptation.
- Decide, with an ADR if yes, whether the provider protocols become public before
  writing `self-host-providers`.

### Weaving the core point and style through the tutorials and guides

The best tutorials carry their project's voice and purpose: Django's newsroom pragmatism,
the Rust Book's patient teacher who expects you to read the compiler, Elm's friendliness,
Julia Evans' delight. pyntpot's purpose is that a computed image should look made by hand,
and the docs can enact that.

- **The arc is the painter's order.** A watercolourist stretches paper, lays a wash, works
  wet then dry brush, draws with the pen, letters last, then composes. Rungs 1 to 7 follow
  that order except that pigment mixing (rung 5) comes after the pen; either move it to
  sit after the brush (a rename of the docstring's rung number only) or frame it as
  returning to the palette. Say so in the opening paragraph and name each section as a studio
  step ("Stretch the paper", "Lay a wash", "Wet brush, dry brush", "Take up the pen",
  "Mix two pigments", "Letter a name", "Compose the sheet"). The map tutorial then reads as
  "the same studio, given a landscape to paint".
- **Use the craft words the code uses, and only those.** Paper tooth, wash, glazing,
  nib, plate, foxing are already in `GLOSSARY.md`; the prose should explain each once in
  the craft sense (glazing is laying a transparent pigment over a dry one) and link the
  glossary, never inventing a synonym.
- **Every page shows a painted image**, including how-tos (the theme guide shows before and
  after; the route-ink guide shows the recoloured line). The images are the project's
  argument.
- **"What to notice" is where the style lives**: the hand-made qualities the engine aims at
  (uneven pooling, broken dry strokes, the lettering's wobble along its line) are named so
  the reader learns to see them, which is also how they will judge their own themes.
- **Voice**: warm, plain, second person, a craftsperson showing an apprentice; no hype, no
  "simply". Determinism is a craft virtue worth stating once: the same seed paints the same
  sheet, so a reader can change one thing and see its effect.
- **Consistency of look**: a hand-lettered heading image or the Patrick Hand face for page
  titles in a future site is tempting; keep it to images the scripts generate so it stays
  tested, never hand-made assets that drift.
