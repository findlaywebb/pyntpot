# Paint around the text, prove every picture

Good documentation for a painting library comes from three things: a strict split of document types, a tutorial ladder in which every step saves an image, and examples that the build executes and the test suite checks. Decorative chrome is not what makes it good. The best creative-coding docs (Rough.js, Manim, matplotlib's sphinx-gallery, Prettymaps) keep a plain, high-contrast reading shell and let **the library's own rendered output** carry the identity. Where hand-made styling reaches the UI itself, as in Excalidraw, it stays on display type, borders and accents, and body text, code and focus rings stay crisp ([webdesignhot: Excalidraw](https://www.webdesignhot.com/design.md/excalidraw/)). For pyntpot's P7 that means painting around the text, never under it. pyntpot renders its own washes, strokes, grain and lettered wordmark. CSS supplies colour from tokens derived from the pigment model, and a build gate checks contrast against the darkest pixel. The tutorials climb from a blank sheet to a composed picture, and the Lynmouth route map is one capstone among several. The biggest obstacle is not in the tooling. Every minimal primitive tutorial currently needs private names (`brush_from_id`, `PaperStyle`, `sheet.rgb`, `PIGMENTS`, `Setting`, `to_img`/`save_webp` and others; repo inventory), so a primitive-first ladder forces a public-API decision and an ADR before the first tutorial page can be written. On tooling, Material for MkDocs reaches end of life on 5 November 2026, which makes **Zensical, pinned, with a separate cached render step** the strongest default, and Sphinx with sphinx-gallery the fallback.

## Four document modes and one reliable path decide quality before any paint

Diátaxis divides documentation along two axes, action against cognition and acquisition against application, giving tutorials, how-to guides, reference and explanation ([Diátaxis compass](https://diataxis.fr/compass/)). Its central claim is that mixing modes is the main failure. NumPy's NEP 44 states the cost plainly: "if explanations are mixed with basic tutorials, beginners might be overwhelmed… if the reference guide contains basic how-tos, it might be difficult for experienced users to find the information" ([NEP 44](https://numpy.org/neps/nep-0044-restructuring-numpy-docs.html)). HoloViz (Panel, hvPlot) mapped a visualisation library's content onto the framework ([PyData Berlin 2025](https://berlin.pydata.org/conferences/2025/PPAYDV.html)), so it is the closest comparable adopter. pyntpot's paths are already fixed as `docs/tutorials`, `how-to`, `reference` and `explanation` (repo inventory), so the structural question is settled. The open question is discipline within each mode.

Diátaxis asks a lot of tutorials. They should **"deliver visible results early and often"**, "maintain a narrative of the expected" by showing exact output, "point out what the learner should notice", "ruthlessly minimise explanation", "ignore options and alternatives" and **"aspire to perfect reliability"**, because the author cannot step in when a learner gets stuck ([Diátaxis tutorials](https://diataxis.fr/tutorials/)). It rejects "basic versus advanced" as the dividing line. The difference is study against work: a tutorial runs one safe line with no choices, and a how-to branches in the messy real world ([Diátaxis: tutorials vs how-to](https://diataxis.fr/tutorials-how-to/)). For pyntpot this settles where material goes. "Paint a flat wash" is a tutorial step. "How to get granulating washes" or "How to match a printed paper size" is a how-to. Why a wash pools at its rim belongs in explanation, next to the existing physical model notes. Perfect reliability, translated into pyntpot terms, means fixed seeds, bundled fonts and the offline Lynmouth fixture. The golden-image culture the repo already enforces supplies exactly that.

Write the Docs adds two principles that matter for an art library. "Current" holds that **"incorrect documentation [is] worse than missing documentation"**, and "Beautiful" holds that "visual style should be intentional and aesthetically pleasing" ([Write the Docs principles](https://www.writethedocs.org/guide/writing/docs-principles/)). On voice, Google's style guide asks for "a knowledgeable friend", second person and imperative, and bans "simply", "it's easy", exclamation marks and "let's" ([Google style: tone](https://developers.google.com/style/tone)). Diátaxis allows tutorial "we" and "Let's check…" ([Diátaxis tutorials](https://diataxis.fr/tutorials/)), so the two conflict. A workable house rule: second person and imperative everywhere, "we" allowed sparingly inside tutorials, and "just", "simply", "easy" and "beautiful results" banned by a lint, in line with the repo's gate culture. The one-name-per-concept rule in `GLOSSARY.md` also limits Write the Docs' "ARID" tolerance for repetition: repeating content is acceptable, repeating with synonyms is not.

## A seven-rung ladder lets maps become one shelf among many

The strongest creative-coding curricula share a shape. The Book of Shaders runs from "Hello world!" through shaping functions, colour and shapes to generative noise and a simulation chapter that includes "Water color", and it closes with a gallery and a glossary ([The Book of Shaders](https://thebookofshaders.com/)). Nature of Code goes from randomness to vectors, forces and agents. It introduces an abstraction only after the learner already holds the concrete thing: it shows that existing `xspeed`/`yspeed` variables *are* a vector. A cumulative "Ecosystem Project" grows chapter by chapter, and each example opens in a web editor with "no installation required" ([Nature of Code](https://natureofcode.com/introduction/)). Every p5.js tutorial card shows a preview image of its result ([p5.js tutorials](https://p5js.org/tutorials/)). Red Blob Games makes concepts explorable by letting "the reader change the *inputs*… and then I show the *outputs*" ([Red Blob Games](https://www.redblobgames.com/making-of/line-drawing/)).

Applied to pyntpot's actual capabilities (repo inventory), the ladder looks like this:

| Rung | Tutorial (one path, one saved image) | Primitives touched | What the learner should notice |
|---|---|---|---|
| 1 | A blank sheet | `Sheet`, paper fibre, cold press | Tooth and grain exist before any paint |
| 2 | One wash, then a wetter one | `wash`, pooled rim, granulation, blooms | Edges darken where water dries |
| 3 | The same path in brush and nib | `Brush`, `stamp`, nib rows, starve/dry flags | One geometry, two media |
| 4 | Two pigments overlapping | `composite`, 15 named pigments, multiply vs Kubelka-Munk | Staining and covering glaze differently |
| 5 | A lettered word on a washed circle | `Hand`, centreline vs outline, slant, curve | Per-seed variation reads as handwriting |
| 6 | A small composed picture | All of the above, foxing, worn border, vignette | Finishing turns a test into a painting |
| 7 | Capstones: Lynmouth route map, botanical plate, card | `Track`, `Basemap`, hachures, `paint`, `compose` | Maps reuse the rungs you already climbed |

Rung 5 matches the planned `examples/word.py` (repo inventory), so the plan already points this way. Borrowing Nature of Code's running project helps: one small Exmoor scene can grow rung by rung, and the route map then arrives as an application of skills the reader already has, not as the library's identity. Since pyntpot is not a browser library, the static stand-in for Red Blob's explorables is the **parameter strip**: one row of thumbnails across wetness, granulation strength or the eight brush treatment rows from wet to bone-dry. pyntpot's existing treatment rows are already such a strip.

The ladder runs into the public API. pyntpot exports `Sheet`, `Canvas`, `Brush`, `stamp`, `wash`, `composite`, `Hand` and the map verbs, yet a ten-line brush stroke, nib line, pigment composite, lettered word or saved file today reaches for `brush_from_id`/`BrushStyle`, `pad.ink_density`, `ink.style.PaperStyle`, `sheet.rgb`, `pigment.PIGMENTS`, `letters.setting.Setting`, `FaceStyle`/`HandStyle`, `nib.plate`, `maps.cache.Cache` or `ink.io.to_img`/`save_webp` (repo inventory). A tutorial that imports private names breaks Diátaxis' reliability promise the moment those names move. There are two honest options. One is to widen the public surface, an ADR amending `0007-public-api`. The other is a thin convenience layer (for example a `Sheet.save` and named pigment and brush lookups) that the tutorials target. Either is a decision for before P7.2, not something to settle in the middle of a tutorial. This is the report's most consequential finding.

## Galleries and executed examples make the art and the proof one artefact

Galleries do a different job from tutorials. Matplotlib's guidance says gallery items "teach by demonstration, rather than by explanation or instruction". It asks for minimal code, 1 to 6 word present-tense titles, 1 to 3 sentence descriptions, and a trailing "References" list that feeds per-function mini-galleries ([Matplotlib: writing documentation](https://matplotlib.org/devdocs/devel/document.html)). Manim, a Python library structurally close to pyntpot, presents each example as **output, then code, then API references**, and links an online Jupyter environment ([Manim examples](https://docs.manim.community/en/stable/examples.html)). Prettymaps, the nearest domain analogue, leads its README with one hero map and uses named presets as its style vocabulary ([Prettymaps](https://github.com/marceloprates/prettymaps)). vsketch, a plotter-art tool whose docs landing page shows none of its art, is the counter-example ([vsketch docs](https://vsketch.readthedocs.io/en/latest/)).

pyntpot has gallery material well beyond maps (repo inventory). It can show pigment swatches with staining and covering transparency, multiply against Kubelka-Munk glazing pairs, brush and nib treatment rows, wash effects (bleed, backruns, pigment separation, the shallow-water pass), paper finishes, and lettering on curves. Shelves should be organised by medium (Paper, Washes, Brushes, Nibs, Pigments, Lettering, Composition) plus Applications, so maps sit on one shelf of seven. Titles should name the artefact ("Graded sky wash"), never "demo of X". A pattern specific to pyntpot that no exemplar quite shows is the **before/after pair**: the raw OSM layer beside its painted wash.

Execution is where pyntpot's existing gates pay off. Sphinx-Gallery runs example scripts at build time, rebuilds only changed examples by MD5 hash, and accepts custom image scrapers ([sphinx-gallery configuration](https://sphinx-gallery.github.io/stable/configuration.html)). Sybil checks code blocks in Markdown and MyST inside an ordinary pytest run ([Sybil](https://sybil.readthedocs.io/en/latest/)). markdown-exec runs fenced Python under MkDocs and Zensical but has no caching ([markdown-exec usage](https://pawamoy.github.io/markdown-exec/usage/)). The robust design for this repo keeps slow renders out of the docs build. Plain `.py` example scripts, each producing one image, are rendered by a cached step keyed on the script hash, the pyntpot version and the fixture paths. A pytest module parametrised over those scripts (with `ids=`) then compares each output with pinned golden values under `--golden-tolerance`. One render path then serves the tutorial image, the gallery thumbnail and the regression test, and a drifted picture fails CI rather than misleading a reader. Sybil or pytest-markdown-docs can cover README and prose snippets. Explicit scripts beat chained doctest sessions here, because chains share state across blocks and `pytest-randomly` will expose the coupling. Under these rules every figure is real output, and the repo already holds candidates in its committed Lynmouth goldens (`paper.webp`, `wash.webp`, `pen.webp`, `labels-centreline.webp`, `map.png`; repo inventory).

## Watercolour identity works as masks plus tokens, gated on worst-case contrast

The finding most relevant to the maintainer's first wish is a caution. I found **no published software documentation site with a watercolour identity**, and no study of how painted UI affects comprehension. The painterly web showcases date from around 2010, and they agree on one lesson: watercolour as accent, with text in the white space ([WebUrbanist, 2010](https://weburbanist.com/2010/07/26/14-artistic-examples-of-watercolor-in-web-design/); [Webdesigner Depot, 2010](https://www.webdesignerdepot.com/2010/03/a-showcase-of-watercolor-in-web-design/)). Documented docs failures are mundane. A grey background behind thin type on Pulp's docs was "difficult/uncomfortable to read" ([Playdate devforum](https://devforum.play.date/t/background-for-pulp-documentation-makes-it-difficult-to-read/1964)). Colour-coded text in the Python docs theme went nearly invisible in dark mode ([python-docs-theme #145](https://github.com/python/python-docs-theme/issues/145)). Colourful painted backgrounds, highlights and titles are achievable, but only if they sit behind large type and in margins, and never behind body copy or code.

WCAG sets the hard edge. SC 1.4.3 requires **4.5:1 for body text and 3:1 for large text** (about 24px, or 18.5px bold), unrounded, and measures contrast against "the specified background over which the text is rendered". Failure F83 names background images directly, and brand guidelines earn no exemption ([W3C Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). SC 1.4.5 wants headings styled with CSS rather than shipped as bitmaps, with logotypes exempt ([W3C Understanding 1.4.5](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html)). That gives a clear split for hand lettering. The pyntpot wordmark can be a painted raster or an SVG path export with `alt="pyntpot"`. Page and section titles stay real HTML text in a display face over a painted wash. Because pyntpot generates the wash, a build step can composite it onto paper and check the text colour against **every pixel** (or the 1st and 99th luminance percentiles), failing below threshold. This "worst-case pixel" gate is my own design inference; WCAG prescribes no method for textures. It matters because pooled rims, the most watercolour-looking feature, are also the darkest pixels.

The technique that best survives theming and accessibility is to **separate shape from colour**. pyntpot emits greyscale alpha masks (ragged wash edges, brush-stroke highlighter strips, painted dividers, a tileable paper-grain tile), and CSS colours them from tokens. `mask-image` has been Baseline since December 2023 ([MDN mask-image](https://developer.mozilla.org/en-US/docs/Web/CSS/mask-image)). `mix-blend-mode` has been Baseline since January 2020 and gives a pigment-like multiply in light mode ([MDN mix-blend-mode](https://developer.mozilla.org/en-US/docs/Web/CSS/mix-blend-mode)). A highlighter behind wrapped text needs `box-decoration-break: clone`, which is still not Baseline and needs the `-webkit-` prefix ([MDN box-decoration-break](https://developer.mozilla.org/en-US/docs/Web/CSS/box-decoration-break)), so give it a flat translucent gradient as the fallback. Avoid live SVG `feTurbulence` filters: animated turbulence was "really sluggish on iOS" and crashed Safari tabs ([GreenSock forum](https://greensock.com/forums/topic/33075-gsap-and-feturbulence-mobile-performance/)), and pre-rendering is pyntpot's native strength anyway. The tokens themselves can come from pyntpot's 15 named pigments (water `#9ec4de`, wood `#a8c286` and so on; repo inventory), darkened in OKLCH until each text or link colour passes 4.5:1 on the paper token. The art and the CSS then share one pigment source of truth. Watercolour tints differ mostly in hue at similar lightness, which is exactly what colour-blind readers lose, so admonitions need icons and labels as well as tints. The Okabe-Ito palette is the reference check wherever categories must be told apart ([Siegal lab, NYU](https://siegal.bio.nyu.edu/color-palette/)).

Dark mode is the hardest problem, and I found no precedent for watercolour specifically. web.dev recommends art-directed swaps through `<picture><source media="(prefers-color-scheme: dark)">` when recolouring falls short, and slightly desaturated imagery, which most surveyed users preferred ([web.dev: prefers-color-scheme](https://web.dev/articles/prefers-color-scheme)). Inverting a watercolour raster turns ultramarine to mud and paper to ink, so do not do it. There are two workable routes. With the mask route, only tokens change: lighter, lower-chroma washes blended with `screen` or `normal`, because `multiply` vanishes on a dark ground. With the content route, gallery paintings sit in framed off-white "paper cards" on the dark page, much as Manim's examples sit on `#ece6e2` ([Manim examples](https://docs.manim.community/en/stable/examples.html)), or pyntpot paints dark-paper variants. Translucent glazes cannot lighten a dark ground, so those variants need body-colour treatment. Under `prefers-contrast: more` and `forced-colors: active`, washes and grain should drop away entirely ([MDN prefers-contrast](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-contrast)).

Page weight is manageable. AVIF ships in every major engine and supports alpha ([web.dev: AVIF](https://web.dev/learn/images/avif)). `image-set()` with `type()` negotiates formats for CSS backgrounds ([MDN image-set()](https://developer.mozilla.org/en-US/docs/Web/CSS/image/image-set)). The two rules that protect Largest Contentful Paint (LCP) are **never lazy-load the LCP image** and preload any above-the-fold CSS background, because the HTML scanner cannot discover it ([web.dev: Optimize LCP](https://web.dev/articles/optimize-lcp)). Washes are low-frequency and compress well. Bake grain or dither into them to hide AVIF banding, reuse three to six heading washes across the site, and let the H1 text, not decorative art, be the LCP element. A budget of roughly 100 KB of decorative imagery per page, 30 KB per asset, is my proposal rather than a sourced norm, but it is a number a test can enforce.

## Zensical with a separate render step is the 2026 default, behind an ADR

The tooling landscape changed under the obvious choice. Material for MkDocs entered maintenance mode with 9.7.0 in November 2025, and its latest release says it **"is scheduled to reach end of life on November 5, 2026"** ([mkdocs-material releases](https://github.com/squidfunk/mkdocs-material/releases)). MkDocs core has not released since 1.6.1 in August 2024, and its 2.0 effort stalled amid governance disputes ([fpgmaas.com](https://fpgmaas.com/blog/collapse-of-mkdocs/)). Zensical, the Material team's successor, is still 0.0.x (0.0.68 on 5 October 2026; [PyPI](https://pypi.org/pypi/zensical/json)). It reads `mkdocs.yml` and keeps "additional CSS, JavaScript, and most template overrides" ([Zensical roadmap](https://zensical.org/roadmap/)), and it natively reimplements mkdocstrings (preliminary, no backlinks), markdown-exec and mike. It does not run arbitrary plugins, and mkdocs-gallery is unsupported and has been dormant since September 2024 ([Zensical plugins](https://zensical.org/compatibility/plugins)). Sphinx 9.1 is the stable alternative with the only mature cached gallery, sphinx-gallery 0.22.1. Furo deliberately exposes only CSS variables for customisation ([Furo customisation](https://pradyunsg.me/furo/customisation/)), so Shibuya or PyData would suit a heavily art-directed look better.

| Concern | Zensical (pinned) | Sphinx 9 + Shibuya/PyData + sphinx-gallery |
|---|---|---|
| Watercolour theming | Material palette tokens, `extra_css`, `custom_dir` block overrides | `templates_path` and CSS; Furo too constrained |
| API reference from docstrings | mkdocstrings-python (preliminary) | autodoc/napoleon or sphinx-autoapi, mature |
| Gallery with thumbnails, back-links | Build it: render script plus snippets | Native, hash-cached, custom scraper |
| Maturity risk | 0.0.x, no Python plugin API yet | Low |
| Authoring | Plain Markdown | MyST or reST |

On balance the pinned-Zensical path wins for pyntpot. The repo's docstrings are already "the agent contract", which mkdocstrings turns directly into reference pages. The gallery's real work, rendering, caching and golden comparison, belongs in a pytest-tested pre-build script under either engine, so sphinx-gallery's main advantage shrinks. Sphinx is the right fallback if mkdocstrings' preliminary support blocks the reference, or if per-function mini-galleries become central. Either way the choice is a boundary-level decision. It needs its own ADR, numbered after the 0013 to 0021 block that P7.3 has reserved for settled decisions (`specs/001-port/plan.md`).

The README follows different rules, because neither GitHub nor PyPI runs CSS. GitHub supports `<picture>` with `prefers-color-scheme` sources and resolves relative paths per branch ([GitHub writing syntax](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)). PyPI's renderer **allows `<picture>` but strips `<source>`**, permits only `http`, `https` and `mailto` schemes, and lets `img` keep only `src`, `width`, `height`, `alt`, `align` and `class` ([readme_renderer clean.py](https://github.com/pypa/readme_renderer/blob/main/readme_renderer/clean.py)). Relative images do not resolve there, so projects pin absolute `raw.githubusercontent.com` URLs to the release tag ([codeanalyzer-python PR #5](https://github.com/codellm-devkit/codeanalyzer-python/pull/5)). The PyPI fallback banner must therefore read well on both light and dark backgrounds by itself, and all watercolour in the README must be baked into images with alt text. A `twine check` plus a grep for relative image paths in built METADATA makes this a gate. For content, put output before prose ([Diátaxis tutorials](https://diataxis.fr/tutorials/); [docsio README examples](https://docsio.co/blog/readme-examples)). Open with a hero grid of *different* subjects (a washed botanical study, a nib sketch, a lettered card, the Lynmouth map), then one sentence, `uv add pyntpot`, a roughly ten-line snippet that saves a PNG with that exact PNG beneath it, and links to the four Diátaxis sections. Every image comes from the same tested scripts, and every example place name stays within the Lynmouth box, which the repo's existing README scan enforces.

## Conclusion

For pyntpot the artistic ambition and the quality discipline turn out to be the same project. A library that paints is the one kind of software whose docs can be decorated entirely with honest output. Its wash masks, highlighter strokes, paper grain, wordmark and every tutorial figure can come from code that the test suite renders and pins, so a regression in the art shows up as a red gate rather than as a stale page. The unusual opportunity is to treat **the docs site as pyntpot's largest integration test**: the pigment model emits the CSS tokens, the contrast gate reads the painted pixels, and the gallery is a golden suite with thumbnails.

The work therefore has a firm order, and the order matters more than any styling choice. First decide the public surface (the ADR amending 0007, or a convenience layer), because no primitive-first tutorial can be written honestly without it. Then come the toolchain ADR and the render-and-golden harness, then the seven tutorial rungs and the medium-organised gallery, and only then the painted chrome, held to headings, margins and dividers and degrading cleanly under dark mode, high contrast and PyPI's sanitiser. What remains unknown is whether readers find painted chrome helpful or distracting. No study measures it, so pyntpot should ship the restrained version first and let real use argue for more paint.
